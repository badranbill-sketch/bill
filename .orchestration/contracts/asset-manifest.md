# Asset manifest 1.0: semantics

- Schema: `asset-manifest.schema.json` (`$id` `https://bill.contracts.local/asset-manifest/1.0`, draft 2020-12). It is generated by `evidence/F02/offers/gen_offers.py`, and the JSON file is the authority.
- Examples: `examples/valid/asset-manifest/` holds the fixture lifecycle and the authoritative empty manifest. `examples/invalid/asset-manifest/` holds 22 files, each with a `.why.txt`. Validation log: `evidence/F02/offers/validation.log`.
- **Status: proposed, submitted, not accepted.** Task F02, offers lane, base HEAD `5cbbf9b5d21dbf03d2cb44e524a6fcdc10d5515b`.
- Proposed document locations (none exists): `content/marketing/asset-manifest.json` (C08 deliverable), and the media manifests `docs/marketing/media-manifest-first-release.json` (C10) and `docs/marketing/media-manifest-quarter.json` (C11), which should use the same schema.
- **Today no asset has a manifest entry.** The authoritative example is an empty `assets` array. It claims nothing exists.
- Sources: 05 §1 (asset fields and statuses), §2–§8 (inventory IDs), §3 (captions are not recordings), §10; 01 §7 (media), §13; 04 §1 (publication authority), CNT01, MED01; D-016, D-052; approval-scopes.md.

## 1. One entry per asset, locale and version

Each entry describes one `(asset_id, locale, version)`. Keeping these unique is a harness rule, AM-HARN-2. A file existing never means the asset is published (05 §1).

| Field | Meaning |
|---|---|
| `asset_id` | Plan inventory ID: `capsule.s01`–`s18`, `companion.s01`–`s18`, `clip.w00`–`w11`, `case.c01`–`c10`, `ink.a01`–`a08`, `template.e01`–`e16`, `ad.ad01`–`ad06`, `ad.rt01`–`rt03`. Otherwise a registry key of letters and hyphens with no digits, one of `article.`, `page.`, `guide.`, `book.`, `event.` or `copy.` (AM-ID-1). The same key form as event-envelope resource codes (event-envelope.md §4.2), so an age or amount cannot be encoded in it. |
| `locale` | `fr`, `en`, or `zxx` for content with no language, such as a drawing without text. French and English are separate entries. |
| `version` | Integer 1–999. A new substantive version gets a new entry; its approval does not carry over. |
| `owner_role` | Who maintains it: an agent role (A0–A6) or `bill`, `arnaud`, `firm_reviewer`. |
| `medium` | `video`, `audio`, `text`, `image`, `print` or `mixed`. |
| `status` | `brief` → `draft` → `reviewed` → `recorded` → `edited` → `approved` → `published` (05 §1). `recorded` and `edited` apply only to audio and video actually recorded in that language (AM-LANG-2). `reviewed` means an editorial or technical review, not a human gate. |
| `language_availability` | `not_recorded` (script only), `language_recorded` (Bill recorded this language), `captions_only` (this locale exists only as captions over another language's recording), `text_only`, `not_applicable`. |
| `captions_source_locale` | For `captions_only`, the other language (`en` for a `fr` entry and the reverse). `null` otherwise. |
| `source_path` | Repo-relative source file (script, copy, SVG). Required from `draft` on (AM-PATH-1). Media masters are not in git (01 §7); their location is in `recording.master_ref`. |
| `factual_claims` | `{present, sources[]}`. Each source has `title`, an `https` URL and an `accessed` date. Sources are required when claims are present (AM-CLAIM-1), with access dates from `reviewed` on (AM-CLAIM-2). The claim-by-claim ledger is C00's. This field records the sources the asset relies on. |
| `offer_refs` | Offers from the offer matrix (`guide-pdf`, `intro-15`, `book-bundle`, `continued-work`) whose terms the asset states. Required when `cta` is an offer (AM-CTA-1). It is also the dependency that voids the approval when that offer changes (approval-scopes.md AS-INV-3). |
| `credential_claims` | `true` when the asset states designations, affiliation, experience or service scope (G1). |
| `rights` | `status` (`pending`, `owned_by_bill`, `licensed`, `created_for_project`, `not_applicable`), `holder` and `evidence_ref`. `synthetic_bill_likeness` is `false` by `const`: no voice clone, avatar or synthetic face of Bill in 1.0 (D-016, AM-RIGHTS-2). |
| `recording` | `null`, or `{master_ref, master_sha256, duration_seconds, recorded_on, consent_ref, captions_sha256, transcript_sha256}`. `duration_seconds` is the **actual** measured length, not the script target. `consent_ref` points at the G4 recording consent (AM-REC-1). |
| `review_hash` | `null`, or `{method, sha256}`: the exact fingerprint the approval binds to. Methods are defined in approval-scopes.md §4.2, and articles use the existing `articles-contentFingerprint-v1`. |
| `approval` | `null`, or `{gates, approved_by_roles, approved_on, record_ref}`. Present only from `approved` on (AM-APPR-5). `approved_by_roles` accepts human roles only (AM-APPR-2). `gates` lists the gate records the approval relies on. |
| `intended_route_key` | Where the asset leads: an existing `lib/routes.ts` key, `ask` (homepage branch only), or a proposed key from routes.md. |
| `cta` | `intro-15`, `guide-pdf`, `book-bundle`, `workshop`, `crossroads`, `share-with-partner` or `none`. One CTA per asset (05 §2, §8). |
| `primary_channel` | `site`, `email`, `linkedin`, `facebook`, `instagram`, `meta_ads`, `live_event`, `workshop` or `print`. |
| `publication_id`, `published_at`, `published_content_sha256` | Only when `status` is `published`, and then required (AM-PUB-1, AM-PUB-2). `publication_id` is the live URL's deploy or provider publication ID; `published_content_sha256` is what the live check observed. It must equal `review_hash.sha256` (AM-HARN-1; 04 §1: publication = live URL or provider ID plus the verified version). |

## 2. Language: recorded versus captions only

05 §3: "Captions in the other language do not count as a recording in that language; mark availability honestly."
- A French entry for a clip Bill recorded only in English is `language_availability: captions_only`, `captions_source_locale: en`, `recording: null`. It can be `draft`, `reviewed`, `approved` or `published` as captions. It can **never** be `recorded` or `edited` (AM-LANG-1).
- The harness checks that a `captions_only` entry has a sibling entry in the source locale that is `language_recorded` (AM-HARN-3).
- Once audio or video is approved or published, it is either a real recording in that language or captions of one (AM-LANG-4). `not_recorded` stays at `brief`, `draft` or `reviewed`.
- An approved or published `language_recorded` entry carries its `recording` evidence (AM-REC-2), and its approval relies on G4 (AM-APPR-4).

## 3. Approval rules

- `approved` or `published` needs a `review_hash`, an `approval` and rights that are not `pending` (AM-HASH-1, AM-RIGHTS-1). The approval's gates always include **G3** (AM-APPR-1). They include **G1** when the asset states an offer or credentials (AM-APPR-3), and **G4** for a Bill recording (AM-APPR-4).
- `record_ref` depends on `manifest_kind` (AM-KIND-1):
  - `authoritative`: `content/approvals.json#<article file>` (existing ledger), `content/asset-approvals.json#<asset_id>@<locale>@v<n>` (proposed) or `.orchestration/approval-packets/…` (proposed, H00). Recording consent: an approval packet, or `owner-storage:<location label>` (proposed reference form for owner-controlled storage, HB-10, HB-22).
  - `fixture`: `fixture:` references only, so fictional examples can never be mistaken for records.
- The same separation applies to `publication_id`, `recording.master_ref` and `rights.evidence_ref` (AM-KIND-2): never `fixture:` in an authoritative manifest, only `fixture:` in a fixture.
- The manifest records approvals. It does not create them. Only the human ledger entries in approval-scopes.md §4–§5 create them.

| AM-PUB-2 | No publication fields before `published` | `publication-id-on-draft` |
| AM-HASH-1 | `approved` or `published` needs a review hash and an approval | `approved-without-review-hash` |
| AM-APPR-1 | Every approval relies on G3 | `approval-without-g3` |
| AM-APPR-2 | Only human roles approve | `agent-role-approval` |
| AM-APPR-3 | Offer or credential content needs G1 | `offer-copy-approved-without-g1` |
| AM-APPR-4 | A Bill recording needs G4 | `recording-approved-without-g4` |
| AM-APPR-5 | No approval before `approved` | `approval-on-draft` |
| AM-CTA-1 | A CTA to an offer lists that offer in `offer_refs` | `cta-offer-not-referenced` |
| AM-LANG-1 | `captions_only` is never `recorded` or `edited` | `captions-only-marked-recorded` |
| AM-LANG-2 | Only recorded audio or video can be `recorded` or `edited` | `text-asset-marked-recorded` |
| AM-LANG-3, AM-LANG-4 | Medium and availability agree; approved media is recorded or captions | covered by the valid lifecycle example |
| AM-REC-1 | A recording cites its consent record | `recorded-without-consent` |
| AM-REC-2 | Approved recorded media carries its recording evidence | covered by the valid lifecycle example |
| AM-CLAIM-1 | Factual claims need sources | `factual-claims-without-sources` |
| AM-CLAIM-2 | Sources carry access dates from `reviewed` on | `reviewed-claim-without-access-date` |
| AM-RIGHTS-1 | No approval with pending rights | `approved-with-pending-rights` |
| AM-RIGHTS-2 | No synthetic Bill likeness | `synthetic-bill-likeness` |
| AM-PATH-1 | From `draft` on, a source file is named | covered by the valid lifecycle example |
| AM-KIND-1 | Authoritative manifests cite real approval and consent records only | `fixture-ref-in-authoritative` |
| AM-KIND-2 | Authoritative manifests carry no `fixture:` publication ID, master or rights reference; fixture manifests carry only `fixture:` ones | `fixture-publication-id-in-authoritative` |
| AM-HARN-1 | Harness: published hash equals review hash | `publication-hash-mismatch` |
| AM-HARN-2 | Harness: `(asset_id, locale, version)` is unique | `duplicate-entry` |
| AM-HARN-3 | Harness: `captions_only` has a recorded sibling in the source locale | checked on the valid lifecycle example |

JSON Schema cannot compare values across entries or fields, so the harness rules are checked by `validate_offers.py`. The C08 manifest check and the proposed `scripts/verify-assets.ts` (approval-scopes.md §4.3) must repeat them.

## 5. Relation to other contracts

- **Event envelope.** `content.draft_created`, `content.approved` and `content.published` use `resource_id = <asset_id>.<version>`, where the version is `v<n>` or `h<sha>`. The envelope's `resource_content_version` pattern accepts `capsule`, `clip`, `case`, `template`, `ad`, `article`, `page` and `guide`. It **does not yet accept `companion`, `ink`, `book`, `event` or `copy`**, which this manifest needs (05 §2 companions, §5 ink, AD06 book, §4 event kit, §11 copy). That is a cross-lane reconciliation item for A0: widen the envelope pattern in a minor version, or map those kinds to existing ones. It is reported in the validation log §5 and not changed here.
- **Offer matrix.** Disclosure wording is `copy.<key>` (offer-matrix.md §2). `offer_refs` uses the offer-matrix IDs.
- **Routes.** `intended_route_key` accepts exactly the existing keys, `ask` and the proposed keys of routes.md. The validation script checks the list against `lib/routes.ts` on main and codex.
- **Counting (CNT01).** C08 counts entries by kind and locale against 05: 18 capsules, 18 companions, 12 clips, 10 cases, 8 ink assets, 13 article packages, 16 templates, 6 static ads and 3 retargeting edits. It then reads the content; file names alone are not enough.
