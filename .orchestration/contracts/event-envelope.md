# Event envelope 1.0: semantics

- Schema: `event-envelope.schema.json` (`$id` `https://bill.contracts.local/event-envelope/1.0`, draft 2020-12). Examples: `examples/valid/event-envelope/` (26 files: one per type, a second-source variant and five content-kind variants) and `examples/invalid/event-envelope/` (24 files, each with a `.why.txt`). Generator: `evidence/F02/data/gen_contracts.py`. Validation log: `evidence/F02/data/validation.log`.
- **Status: proposed, submitted, not accepted.** No event system exists in the repository today (inventory §3). Paths below are proposed: the P02 deliverables in the task ledger are `lib/marketing/`, `app/api/marketing/` and `app/api/internal/automation/`, and events are persisted in the proposed `integration_events` table (`operational-data-model.md`).
- Source: 04 §3 (envelope, 20 types, rules), 04 §1 (authority), 01 §9 (workshop), D-014, D-040.

## 1. What an event is

An event records one accepted action or one verified external fact. The server creates it inside the same transaction as the authoritative record and any delivery jobs (04 §4). Browsers never emit envelopes: a `site.*` source means "a server-side handler that validated a public form".

The envelope is the whole event: there is no payload. Anything a consumer needs beyond these ten fields it reads from the authoritative table by ID, through a scoped server operation.

## 2. Fields

| Field | Required | Format | Meaning |
|---|---|---|---|
| `schema_version` | yes | `"1.0"` | Consumers reject any other value. |
| `event_id` | yes | UUID v4 or v7, lowercase | Generated by the server; unique. |
| `type` | yes | one of the 20 types | See §3. |
| `occurred_at` | yes | RFC 3339 UTC with `Z` (`2026-10-02T14:00:00Z`) | When the fact happened (the provider's time for provider events). Offsets are rejected; America/Toronto is for display only (D-044). |
| `subject_id` | yes | `con_`, `cnt_` or `job_` + 26 Crockford base32 | The entity the event is about. The type fixes which prefix. |
| `locale` | yes | `fr` or `en` | Language of the person or content concerned. |
| `source` | yes | closed enum (§5) | Where the fact came from. The type fixes the allowed subset. |
| `resource_id` | yes | versioned registry code or entity ID (§4.2) | What the event concerns: a guide or workshop version, a consent wording, a webinar, order, right, booking, content version or template version. A registry code must also be a registry entry (EV-REG-1). |
| `consent_reference` | per type | `cev_` + 26 | Required on `marketing.opted_in`, `marketing.withdrawn`, `workshop.completed`; forbidden on every other type. |
| `idempotency_key` | yes | `ik1_` + 64 lowercase hex | Stable key for this accepted action (§4.3). |

`additionalProperties` is false: no form body, no free text, no financial field, no attendance guess can be added.

`workshop.completed` is a minimal, optional, consented signal. It carries no answers, calculated gap, selected financial-warning clip or inferred diagnosis (04 §3). A self-selected topic is not in 1.0 (privacy-boundary.md PB-FIN-8).

**Booking events need a joined contact (EV-BOOK-1, repair attempt 3, A6D2-02).** `meeting.confirmed`, `meeting.cancelled`, `meeting.held` and `consultation.redeemed` require a `con_` subject.
- They are emitted only for a booking joined to a contact by the exact-address rule of authority-matrix.md AM-BOOK-3.
- The join happens on the application server before the envelope is built (operational-data-model.md §4, `op_accept_event`). Neither the envelope nor its `origin_ref` ever holds the invitee address.
- A booking that matches no contact produces no envelope and no job. Its row is stored unmatched and waits for the operator's reconciliation (AM-BOOK-5).
- A later operator join emits `meeting.confirmed` with source `operator.reconciliation` and the `aud_` ID as origin (§4.3).
- So `already_booked` (E05, E11) and the E15 and E16 jobs apply to joined bookings only (AM-BOOK-6).

## 4. Identifiers

### 4.1 Internal IDs
`<prefix>_` + 26 lowercase Crockford base32 characters (`0-9a-hjkmnp-tv-z`, no `i l o u`), from a CSPRNG; a ULID is permitted. Prefixes: `con` contact, `cev` consent event, `wev` webinar event, `reg` registration, `ord` order, `rgt` consultation right, `bkg` booking, `job` delivery job, `cnt` content item, `aud` audit event, `opr` operator. The format has no `@`, `.`, space or currency symbol, so an email, amount or age cannot appear in its ordinary written form. IDs are opaque; nothing may be encoded in them.

### 4.2 Resource codes
Registry codes have the form `<kind>.<key>.<version>`. What the schema accepts depends on who the event is about.

**Contact-subject codes (EV-ID-2, PB-ID-3).** These are the guide (`guide.requested`), the workshop (`workshop.access_requested`, `workshop.completed`) and consent wordings (`marketing.opted_in`, `marketing.withdrawn`).
- The key comes from a closed set: guide `retirement-guide`, workshop `retirement-workshop`, consent purposes `nurture` and `workshop-followup`.
- Each set is proposed. The guide and workshop keys follow the EN slugs of the existing `resources` route (`lib/routes.ts`) and the proposed `workshop` route (routes.md). The consent purposes are pending G5.
- Adding a key is a contract change (1.1, recorded by A0).
- The version is always `h` plus 12–64 lowercase hex of the approved artifact's sha256 (the guide edition, the deployed workshop build, the exact consent text shown). `v<number>` is rejected here.
- So a word, name, age, amount or diagnosis cannot be written into these codes in readable form. The invalid examples `age-in-resource-id`, `amount-words-in-workshop-key`, `diagnosis-in-workshop-key`, `age-in-guide-version`, `name-as-guide-key` and `consent-wording-mutable-version` prove it.
- The schema still cannot tell a real hash from a number written in hex. EV-REG-1 closes that gap.

**Content-item codes.** These are `content.draft_created`, `content.approved` and `content.published`, with subject `cnt_`.
- The code is any asset-manifest 1.0 `asset_id` plus `.v1`–`.v999` or `.h<hex>`. The fixed inventories keep their plan IDs: `capsule.s01`–`s18`, `companion.s01`–`s18`, `clip.w00`–`w11`, `case.c01`–`c10`, `ink.a01`–`a08`, `template.e01`–`e16`, `ad.ad01`–`ad06`, `ad.rt01`–`rt03`. The other kinds (`article`, `page`, `guide`, `book`, `event`, `copy`) use a key of letters and hyphens with no digits.
- These codes describe editorial items and never a visitor. The v-form is kept for drafts. Anything approved at G3 uses the hash form.
- The ID alternation is a copy of the asset-manifest pattern. The data-lane harness checks that the two stay byte-identical (repair attempt 2, A6D-06).

**Template codes.** `delivery.failed` uses `template.e01`–`e16` plus a version.

**EV-REG-1: registry membership (runtime, PB-ID-5).** Every registry code in an accepted envelope must be an entry of the approved resource registry. Otherwise the envelope is rejected whole (EV-REJ-1).
- The registry is proposed. P02 chooses its location: a generated read-only list shipped with the build, not a Supabase table.
- P02 builds it only from approval records: G3 hashes from the asset manifest and H00 packets for guide, workshop and content versions, and G5 records for consent wordings.
- Each entry holds `resource_id`, `kind`, `key`, `version`, `locales` and an `approval_ref`.
- For `site.*` sources the server sets the code from the entry of what it served, never from the request (PB-ID-6).
- Tests: AUTH05 (a well-formed but unregistered code such as `workshop.retirement-workshop.h850000000000` is rejected), WK04, P02 unit tests.
- A fictional registry for this lane's examples is in `evidence/F02/data/fixture-resource-registry.json`. The harness shows every valid example's code is a member, and that an unregistered well-formed code is not.

### 4.3 Idempotency key
`ik1_` + lowercase hex HMAC-SHA256 of the canonical tuple, fields joined by a line feed:

```
type \n subject_id \n resource_id \n origin_ref
```

| Source family | origin_ref |
|---|---|
| `site.*` | the form's `request_id`: a UUID v4 generated in the browser per submission and kept across retries, like the existing inquiry `requestId` (`lib/contact.ts`) |
| `provider.*` | `<provider>:<provider event ID>`; for calendar polling, the event ID plus the provider's version or etag |
| `operator.*` | the `aud_` ID of the audited operator action |
| `editorial.*` | the content sha256 plus the ledger entry (PR number or packet path) |
| `system.dispatcher` | the `job_` ID plus its `attempt_count` |

The HMAC key is a server-only secret, proposed name `EVENT_KEY_SECRET`, entered by the authorized operator in the application server-only environment. It is a new entry for the secret-location map (HB-07, D-070) and is never in chat, git or logs. The `ik1` prefix versions the key; a rotation starts `ik2` and keeps accepting `ik1` for replays.

The key dedupes replays of one origin. Different origins that describe the same fact (for example two Stripe event types for one payment) are deduped by domain uniqueness: one paid transition per order, one right per order, one registration per contact and event (authority-matrix.md AM-PAY-2).

## 5. Source codes

| Source | Meaning | Authentication (owner) |
|---|---|---|
| `site.guide_request`, `site.webinar_registration`, `site.workshop_access`, `site.workshop_completion` | Server handler for a validated public form | Origin check, content-type, size and rate limits, strict schema (P02, AUTH03); the codex inquiry route is the precedent |
| `site.consent_capture` | Explicit opt-in control on any form | Same, plus the displayed wording version |
| `site.optin_confirmation` | Confirmation link click (if double opt-in is chosen at G5) | Opaque hashed token (PB-URL-2) |
| `site.preferences`, `site.unsubscribe` | Preferences page, one-click unsubscribe | Opaque hashed token |
| `site.join_redirect` | Join page click-through | None needed; it asserts nothing but a click |
| `provider.stripe_webhook` | Stripe webhook | Signature over the raw body, event ID dedupe (S10) |
| `provider.brevo_webhook` | Brevo unsubscribe, blocklist, bounce or delivery signal | Provider authentication as verified at P05 (unverified here) |
| `provider.booking_sync` | Authenticated calendar or scheduler read or callback | OAuth or provider signature (P05); if none is reliable, the operator's daily reconciliation is used instead |
| `provider.meet_attendance` | Meet attendance report | Only if the account's tier really offers it (07 S5); otherwise unused |
| `operator.reconciliation`, `operator.fulfilment`, `operator.suppression` | Authenticated operator in the operations view | Session plus audit row (U05) |
| `editorial.draft_job`, `editorial.approval_ledger`, `editorial.publication_handoff` | WF08, the Git approval ledger or H00 packets, WF09 after the live check | Repository protections (HB-11) |
| `system.dispatcher` | WF02 dispatcher outcome | Automation service token (06 map) |

Existing `proxy.ts` (identical on every branch) requires review Basic Auth on every non-static route until `launchApproved()`. Provider callback routes (proposed under `app/api/marketing/`) may be excluded from it only narrowly, and only because they enforce their own signature or token check (04 §4). An obscure URL is not authentication. The matcher already skips `/assets/`, which is a separate open issue (TB-09).

## 6. Consumer rules

- **EV-REJ-1.** An envelope that fails the schema is rejected whole: no partial write, no side effect, a sanitized error code in the log.
- **EV-REJ-2.** A valid envelope with an idempotency key already stored returns the stored outcome and causes no new side effect.
- **EV-REJ-3.** Unknown `schema_version` or `type` values are rejected, not stored for later.
- **EV-REG-1.** A schema-valid envelope whose registry-code `resource_id` is not in the approved resource registry is rejected whole (§4.2, PB-ID-5). Entity IDs (`wev_`, `ord_`, `rgt_`, `bkg_`) are instead checked against their own table rows.
- **EV-BOOK-1.** A booking event is produced only for a booking joined to a contact (§3, authority-matrix.md AM-BOOK-3). A producer that cannot make the join emits nothing and stores the booking unmatched (AM-BOOK-5). It never uses a placeholder contact and never takes the subject from a name or a click.
- **EV-ORD-1.** Consumers do not assume arrival order. They compare `occurred_at` and current record state (for example a `meeting.cancelled` older than the booking's latest confirmation is recorded but does not cancel it).

## 7. Versioning

Any change to a field, a pattern, the type enum, the source enum or a per-type rule makes a new contract version (`1.1` for additions consumers can reject safely, `2.0` for changes of meaning). Producers and consumers ship the new version together; `schema_version` tells them apart. A0 records the version change in `decisions.md`.

## 9. Changes in F02 repair attempt 2 (design review `reviews/F02-design.md`)

These changes were made inside 1.0 before acceptance, so no consumer has built against the earlier draft (§7 applies from acceptance on).
- A6D-03: `resource_guide_version`, `resource_workshop_version` and `resource_consent_wording` now take a closed key and a hash-only version (§4.2). EV-REG-1 and PB-ID-5 add registry membership as a runtime rule. Five invalid examples were added, one for each encoding the review showed was accepted, plus a v-numbered consent wording. The valid examples now use `retirement-guide`, `retirement-workshop` and a hash-versioned consent wording.
- A6D-06: `resource_content_version` now accepts every asset-manifest 1.0 asset ID. Five valid content-kind examples were added (companion, ink, book, event, copy).
- Unchanged and still open: `zxx` assets (README XL-02), because the task fixes the envelope locale to `fr` or `en`; the v-form on `delivery.failed` template codes (XL-16).
