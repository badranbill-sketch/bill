# Feature flags and readiness states (contract 1.0)

- Schema: `feature-flags.json` (`$id` `https://bill.contracts.local/feature-flags/1.0`). It is a JSON Schema for one environment's flag and readiness document. It is generated by `evidence/F02/data/gen_contracts.py`, and the JSON file is the authority. Examples: `examples/valid/feature-flags/` (5, including the all-off defaults) and `examples/invalid/feature-flags/` (14, each with a `.why.txt`).
- **Status: proposed, submitted, not accepted.** The environment variable names other than `PUBLIC_LAUNCH` are proposed. Where the runtime document lives is proposed below. No flag has been switched and no readiness state is recorded.
- Sources: 04 §7, 01 §7 (flags default off), §16 (gradual rollout), 06 gate registry, D-035, D-036, TB-16.

## 1. What exists in the repository today

Checked against codex `66cce52`; `lib/business.ts` is the same blob on main.
- `PUBLIC_LAUNCH` (environment variable) and `launchApproved()` in `lib/business.ts`. `launchApproved()` returns true only when `PUBLIC_LAUNCH === "true"` **and** all eight `business.approvals` are true: `businessDetails`, `serviceScope`, `qualificationsAndAffiliation`, `portraitRights`, `websiteCopy`, `privacyPolicy`, `legalNotices`, `contactOperations`. All eight are false. `proxy.ts` uses it to require review credentials; `scripts/launch.ts` blocks while any is false (D-061, TB-04).
- `business.newsletterEnabled = false` and `business.analyticsEnabled = false`; `scripts/launch.ts` refuses a launch if either is true.
- `ENABLE_CONTACT` gates the existing inquiry adapter.
- There is no five-state model (TB-16).

This contract **adds** a model and does not replace any of this. Proposed mapping, for A0 to apply, because `lib/business.ts` is a locked shared file (D-065):
- `public_launch` ↔ `PUBLIC_LAUNCH`; `launchApproved()` stays as it is and remains an additional requirement;
- `marketing_dispatch` covers what `newsletterEnabled` would have enabled;
- `third_party_tracking` ↔ `analyticsEnabled`.

## 2. The six switches

All default `false` (schema `default: const false`). Any authorized operator may set any flag to `false` at any time as a kill switch, without a gate. Setting a flag to `true` needs the gates listed, recorded by humans, and `enable_evidence_ref` pointing at the record (in production, the G6 release record).

| Flag | Env var | What it switches on | Capabilities it requires ready (`controls`) | Gates to enable (production) | Rollout step (01 §16) |
|---|---|---|---|---|---|
| `public_launch` | `PUBLIC_LAUNCH` (existing) | The public site: no review credentials, indexing allowed, public forms accept real people | `public_site`, `preferences_unsubscribe` (which must also be enabled) | G1, G3, G5, G6, plus the eight existing approvals | public guide and meeting path |
| `checkout_live` | `CHECKOUT_LIVE` (proposed) | Stripe **live** mode for the book, with fulfilment and redemption | `book_checkout`, `book_fulfilment_messages`, `consultation_redemption` | G0 (price, cap), G1 (wording), G2 (Stripe live account), G3 (offer page and terms hash), G5 (fulfilment and refund process, HB-28), G6 | capped book sales |
| `marketing_dispatch` | `MARKETING_DISPATCH` (proposed) | The dispatcher may send promotional jobs. Every promotional job needs it, whatever capability owns it (FF-RUN-2), including a promotional E09. It is also a controlling flag of every job of the nurture and workshop follow-up capabilities, including the operational E02 opt-in confirmation, which exists only to serve nurture | `marketing_nurture`, `workshop_followup`, `preferences_unsubscribe` (which must also be enabled) | G2 (sending account and budget), G3 (templates), G5 (consent wording, classification), G6 | workshop and event acquisition |

| `third_party_tracking` | `THIRD_PARTY_TRACKING` (proposed) | Loading third-party measurement on non-workshop routes | `third_party_measurement` | G5 (consent approach, processor), G6 | only with an approved measurement plan |

## 3. The five readiness states

Every capability records all five, separately (schema rule FF-STATE-1). None implies another (AM-FLAG-1).

| State | Means | Evidence (`evidence_ref`) | Who may record it | Invalidated by |
|---|---|---|---|---|
| `code_ready` | The implementation passed its local checks and A6's review at stage `local_implementation_tested` | review file and commit | A0 after A6 evidence | a code change to that capability |
| `provider_tested` | It worked against the real provider in authorized staging or test mode (fixture ≠ sandbox ≠ live) | `.orchestration/provider-evidence/…` | A6 or A4 with the operator | a provider account, credential or version change |
| `approved` | The human gates for enabling it **in this environment** are recorded: G2 action scope for staging tests; the production gates in the table in §4 | approval packet or gate record, plus `gate_refs` and `scope_hashes` | human roles only (`bill`, `firm_reviewer`, `arnaud`, `privacy_owner`, `account_owner`; FF-APPR-1) | a change to any hashed asset or config it covers, and only that change (04 §7) |
| `enabled` | It is switched on in this environment's deployed configuration | release or deploy record | the operator | a deploy that turns it off |
| `live_verified` | A production smoke test observed it working for real (for example an allowlisted inbox received the message) | live evidence file | A6 with the operator | any change that invalidates `enabled` or `approved` |

A state set to `true` must carry `evidence_ref`, `recorded_at` and `recorded_by` (FF-STATE-2). Examples use `fixture:` references and are fictional.

## 5. Invariants (schema-enforced)

| ID | Rule |
|---|---|
| FF-DEF-1 | Every flag's `default` is `false`. |
| FF-SHAPE-1 | Exactly six flags and seventeen capabilities; nothing else. |
| FF-GATE-1 | Each flag's `env_var`, `controls` and `enable_gates`, and each capability's `controlling_flags`, `templates`, `provider_required` and `enable_gates`, are frozen by `const`. A document cannot weaken them. |
| FF-STATE-1 | All five states are present on every capability, each as an object; one boolean cannot replace them. |
| FF-STATE-2 | A true state carries evidence, a time and who recorded it. |
| FF-APPR-1 | `approved` is recorded by a human gate owner, never an agent role. |
| FF-APPR-2 | A true `approved` names at least one gate and at least one sha256 scope hash. |
| FF-INV-1 | A capability is `enabled` only if it is `code_ready`, `approved` and (if it uses a provider) `provider_tested`. In production, all of its controlling flags must also be true. Outside production, `public_launch` and `checkout_live` are replaced by the environment substitute of FF-RUN-1 (review protection, an allowlist, Stripe in test mode); its other controlling flags must still be true. The runtime gate (§5.1) applies exactly the same rule, so a document that validates acts as it states. |
| FF-INV-2 | `live_verified` requires `enabled`. |
| FF-INV-3 | A flag is true only if every capability it `controls` is `code_ready`, `approved` and `provider_tested` where applicable. `public_launch` and `marketing_dispatch` also require `preferences_unsubscribe` to be enabled. Since repair attempt 2, `marketing_dispatch` controls `workshop_followup` too (invalid example `marketing-dispatch-without-workshop-followup-ready`). |
| FF-GATE-2 | Every flag except `public_launch` lists in `controls` each capability that names it as a controlling flag. `public_launch` controls only `public_site` and `preferences_unsubscribe`, because public capabilities are rolled out one by one after launch (01 §16) and each one's own FF-INV-1 already requires `public_launch`. This is checked by the data-lane harness, not by the schema. |
| FF-ENV-1 | Outside production, `public_launch`, `checkout_live`, `paid_ads` and `third_party_tracking` are false. |
| FF-ENV-2 | Outside production, every `live_verified` is false. |
| — | A capability with no provider keeps `provider_tested` false: it means "not applicable" there. |

### 5.1 Runtime gate (FF-RUN), for downstream code (P00, P02, N02)

These rules replace the earlier one-line runtime rule, which gave no non-production waiver and so contradicted FF-INV-1 (repair attempt 2, A6D-01). `job-state-machine.md` §6 step 2 and `email-eligibility.json` PSC-3 cite these rules. `email-eligibility.json` `runtime_gate` holds them as data.

| ID | Rule |
|---|---|
| FF-RUN-1 | **Capability gate, every environment.** A capability may act (claim or send a job, accept its form, create a checkout, publish) only when all of these hold in the running configuration. (a) Its `enabled` state is true in this environment's approved document, and the running variables match that document (§6). (b) In production, every one of its controlling flags is true. (c) Outside production, every controlling flag other than `public_launch` and `checkout_live` is true. Those two are replaced by the **environment substitute**, which has four parts. The environment is not production. Access is limited to reviewers: the existing `proxy.ts` review protection applies, because `launchApproved()` is false while `PUBLIC_LAUNCH` is not `"true"`, or the environment is a local development machine. Every send goes only to a G2-allowlisted recipient (PB-ENV-2; pre-send step 3, PSC-5, suppression `not_allowlisted`). Stripe uses test-mode credentials, so a live-mode key outside production refuses to start the capability. This is exactly FF-INV-1, so the valid example `staging-guide-delivery-allowlist-test` can send E01 to an allowlisted inbox (MAIL01), and book checkout can run in Stripe test mode in staging (PAY01, `provider_tested` evidence). |
| FF-RUN-2 | **Promotional kill switch.** Every promotional job needs `marketing_dispatch` true, whatever capability owns it and in every environment. `marketing_dispatch` is never waived. With it false, every promotional job is deferred at its pre-send check (T7, `defer_reason` `capability_disabled`). This includes a promotional E09 owned by `event_lifecycle`. Every job of `marketing_nurture` and `workshop_followup` is deferred too, through FF-RUN-1, because those capabilities list the flag, and that includes the operational E02. |
| FF-RUN-3 | **When a kill switch takes effect.** A flag set to false applies at the next pre-send check or request. A job already leased is checked again before `send_started_at` (job-state-machine.md §6), so no new provider call starts once the change is deployed. Deferred jobs are not cancelled. They wait for `next_attempt_at` and expire at their own `expires_at`, so a reminder is never sent late. Throwing the switch takes two steps. First, the operator sets the running variable to false, which takes effect at once. Then the operator records a document in which the flag is false and every capability that lists it is no longer `enabled` (FF-INV-1 requires this; §3 says a deploy that turns a capability off invalidates `enabled`). Until that document is recorded, the mismatch rule of §6 keeps the affected capabilities stopped. A mismatch never enables anything. |

Outside production, every send also requires an allowlisted recipient, whatever the flags say (PB-ENV-2). The data-lane harness (`evidence/F02/data/validate_f02_data.py` §7) runs a reference implementation of FF-RUN-1 and FF-RUN-2 against the valid flag examples. It checks that FF-RUN-1's non-production flag set equals the one the schema enforces for `enabled`.

## 6. Where the documents live (proposed)

- Production: the flags section of `.orchestration/release.json` (L04), one document per release, approved at G6 and hash-referenced by `enable_evidence_ref`.
- Staging and development: a document per environment committed with the deployment profile (P00, `infra/deployment/`, proposed), with fictional or allowlist-scoped evidence only.
- The deployed runtime reads environment variables. P00 and P02 must add a check that the running variables match the approved document. A mismatch refuses to start the affected capability; it never enables it.

## 7. Changes in F02 repair attempt 2 (design review `reviews/F02-design.md`)

- A6D-01: the runtime rule now grants the same non-production substitute as FF-INV-1 (§5.1, FF-RUN-1). `job-state-machine.md` §6 step 2 and PSC-3 cite it, so the allowlisted staging send in `staging-guide-delivery-allowlist-test` is possible under one rule.
- A6D-07: FF-RUN-2 makes `marketing_dispatch` a requirement of every promotional job, whatever its capability. `marketing_dispatch.controls` now includes `workshop_followup`, so FF-INV-3 checks its readiness. New examples: valid `production-marketing-dispatch-fictional` and invalid `marketing-dispatch-without-workshop-followup-ready`. The operational E02 staying behind `marketing_dispatch` is intended (§2) and documented, not an asymmetry.
